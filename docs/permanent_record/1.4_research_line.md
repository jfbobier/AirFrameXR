# The 1.4 research line (archived 2026-11-07)

**Where it is.** The tag `archive/1.4-picture-edges` (commit b849241, on GitHub) and the pre-release `v1.4.0-alpha.1`. The `1.4` branch was deleted from GitHub on 2026-11-07; the tag keeps every commit. Restore a working branch with `git checkout -b 1.4 archive/1.4-picture-edges`. Nothing of it is in the 1.3.5 engine (the host differs from v1.3.4 by its version string).

## What it tried

- Three boxes per eye: P (the panel), V (the headset view: what the stream covers), G (what the game renders); the PC decides all three. Design: `docs/PICTURE_EDGES_DESIGN.md`, `docs/FOV_APERTURE_PLAN.md`, `docs/END_TO_END_FOV_DESIGN.md` (on the tag).
- A headset view message to our client over `ServerControlPacket::Reserved` (`tools/patches/headset-view-message.patch`, `client-reserved-message*.patch`, the visionOS fork's branch `1.4`): the client declares min(P, V), the stream is sized over V.
- A per-game honour check (`tools/host/src/fov_intake.rs`, IPC v37 to v39, `config\fov_verdicts.json`, the whitelist): a game is told G only after it has been seen to follow the box.
- A per-eye restriction (`fovScale[2][4]`, IPC v38) and a per-eye fit in the profile store.
- A Swift headset for the lab (`harness/swift_headset`, `swift_headset_check.py`): the visionOS client's own code with the real `client_core`, run on Linux.
- Lab scenarios (`e2e_fov_policy_*`, `e2e_fov_game_*`, `e2e_fov_headset_view`, `e2e_fov_stream_*`) with fake games modelled on UEVR, the Uncharted and Gravity Rush 2 mods.

## Why it was retired

- On a real headset (2026-11-06) End of Abyss showed a wrong parallax and a slightly tilted picture. The host log shows the two eyes were told different boxes: left 0.592 / 0.757 / 0.659 / 0.552 against right 0.677 / 0.756 / 0.684 / 0.526 (21:54), and a right eye 18 to 20 % smaller vertically than the left (21:57). A mod that assumes near-mirror eyes cannot take that.
- A custom headset view showed a doubled image; the cause was never found (the client re-declares its view mid-stream when the message arrives; the per-eye values are the suspects).
- The black-bar fit measured far too small (about 27 % of Apple's frustum against 35 % for the author's rays): a thin black bar on a dark lens housing cannot be seen. The line test of 1.3.5 replaced it.
- The honour check was complex and irrelevant for the Vision Pro, where the headset view and the restriction are the same box in practice.

## What came back into 1.3.5

The line test (`xr_tool.h`, `calibrate.exe`), the radio choice with AVP optimized, the foveation from Apple's rate map (now milder than ALVR's defaults and following the restriction), the desktop mirror's controls, its confirmed-controller beam and pointer dot, the orphan-probe guard, the lab's tool scenarios, `ratemap_check` and the Python oracle.

## What is worth reviving

1. The headset view message **with one mirrored box only**, for the sharper stream without the client slider: test a mirrored view on a headset first; the per-eye box is what broke.
2. The phase lock's open-loop guard (host commit 07afe93 on the tag): the lab's mock headset never follows a slide, so the lock slides for ever; `e2e_baseline` fails three pacing checks without it.
3. The honour check, only if a game that ignores the restriction proves a real problem.
4. The Swift headset harness, for testing the client's code without a headset.

## Lessons

- Never tell a game a different box per eye. After a run, the left and right boxes in the `game submitted` log line must mirror each other.
- Measure a window by something that disappears (a bright line), not by a bar that appears.
- A tool scene must end with the tool window (a parent-pid check): an orphaned probe made every new host fail with `OpenSharedResource` in a restart loop.
- On the 5090 builder the ALVR source keeps patches between builds; reverse the other branch's patches before building (the client lab failed on a `ReservedMessage` variant it did not handle).

# AirFrameXR 1.3.6: a launcher that cannot write NaN, and a switch for a sharper stream over a smaller view

The engine is [1.3.5](v1.3.5.md)'s (the host differs by its version number). 1.3.6 is launcher fixes and one switch, from a field report: the stock client at FoV Scale 0.6 looked much sharper than ours at 1.0.

## What is new

- **The streamer starts again after a small view.** Choosing a restriction as wide as the picture the headset declares (the stock client at FoV 0.6 declares 1.05 / 0.61 / 0.72 / 0.61) gave the foveation a centre as large as the frame and a shift of `NaN`, which was written into `config\session.json`: the host refused to start (`session.json is not valid JSON`, exit code 7). Now a band as wide as the frame has a shift of 0, and neither the foveation nor the launcher's JSON writer can write NaN or Infinity.
- **A restriction that restricts nothing no longer shrinks the stream.** With such a restriction on, the foveation had nothing to compress, so the stream, sized for the bitrate, fell to 1984 x 1600 over the 0.6 box (about 1195 px per unit of tangent). It now follows Apple's map alone: 2368 x 1920 (about 1430 px/tan) at the same 6.4 Mpx encoded.
- **New switch, *Keep the stream as big as the whole panel's*** (*Advanced video and performance settings > Stream size*, `video.stream_keep_panel_size`, off by default, restart of the streamer). On: the stream is sized for the whole panel (what the headset declares at FoV 1) whatever view it declares now, so a smaller view (the client's FoV Scale) puts the same pixels on less angle, as the stock client does. For the 0.6 box that is 3040 x 2432 (about 1830 px/tan; the old stock client's stream carried about 1640 at its centre) **at 10.4 Mpx encoded against 6.4 Mpx**: 0.29 bits per pixel instead of 0.47. Check the encode time and the headset's decode before keeping it.
- The foveation line in the log now says the encoded size.

## Why the stock client looked sharper

Both clients declare the compositor's frustum times their FoV Scale, and the streamer sends the same number of pixels either way, so 0.6 is about 1640 px/tan and 1.0 about 970. The Vision Pro lens shows about 1.7 x 1.3 tan; the full frustum is 2.8 x 2.2, so about 65 % of a FoV 1 picture is outside what the lens shows. The trade-off is the edge of the view: at 0.6 the nose side is cut at 0.61 where the author's calibrated window reaches 0.71 (about 4 degrees). The stock text says it plainly: increase FoV for timewarp comfort, or sacrifice FoV for sharpness.

## Rebuilt the same day: the Advanced window opens

The first 1.3.6 zip (built from commit f837f2e) had a bug found within the hour on the author's PC: clicking *Advanced video and performance settings* did nothing. The new switch had been declared in a section the window never built, so loading its value threw and the window was never shown. The zip now on this page is the rebuild from commit 393a810: the section is built, and the window refuses to open with a clear message if a switch is ever left without a control. The tag `v1.3.6` was moved to that commit. The check that catches it (`uitest.exe --only advanced-switches`, 9 renders) passes; it was not run before the first zip, only the compile check.

## What ran, and what did not

The GUIs compile (`check_gui.sh`). A probe against the real `PipelineModel.cs` gives the numbers above (275 Mbps, 90 Hz, the 0.6 box): the old code reproduces the 1984 x 1600 of the field report exactly. **Not run on a headset:** the switch, the sharper look it should give, the Vision Pro's decode at 10 Mpx. The switch's pixel numbers are a model, not a measurement.

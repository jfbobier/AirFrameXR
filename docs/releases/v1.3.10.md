# AirFrameXR 1.3.10: one logging framework, the headset's own tick counts, arrow keys for the desktop mirror

## What is new

- **One logging framework.** A single writer thread per process owns the log files and the frame path never waits on the disk (a full queue drops the line and says how many). `logs\\AirFrameXR.log` is the one general log (ALVR's own lines are in it as `[alvr]`; the raw ALVR stream, `[STATS]` and the CSVs are in the debug folder only), rolled over daily and kept 7 days. **Each game run has its own log**, `logs\\games\\<exe>\\<yyyymmdd-hhmmss>.log` (the last 20 per game), with its timeline lines (frame generation perf, memory, `headset ticks`). Verbosity: `log_level` in `airframexr.json` (error, warn, info = default, verbose, debug) or `--log-level`; the old debug switch is the `debug` level. The shim's lines reach the host through a ring buffer in the IPC block (IPC version 37: host and shim of different builds refuse each other, they ship together). The stats window, its timeline and the game record (`log` field of a session) read the run log. The desktop mirror writes its own per-run log (`logs\\mirrordesktop\\`), the windows write `logs\\ui\\<time>-<window>.log` (windows, DPI, unhandled exceptions, the commands sent to the streamer).
- **"Headset repeated" from the headset's own count.** The new visionOS and Quest clients count every display tick and send one `va_ticks` line every 10 s (existing ALVR client log packet: no protocol change). The streamer uses it when it is there and keeps the old gap-based figure for any other client. The first field sessions decide whether the old figure was inflated (10 to 13 % against 3 to 4 % on the headset's counters).
- **Desktop mirror: arrow keys.** The left controller's thumbstick and an Xbox pad's D-pad send arrow keys, one per push (hold = one key, push again for the next). The right thumbstick still scrolls; **the left one no longer scrolls**. The controls panel lists it. If the captured screen never delivers a picture the mirror says so in its log after 3 s, and shows the first frame even when the screen is idle.
- **Game statistics: "headset shows"** is the headset's display rate times the share of its display ticks that showed a new frame, not the count of unique frame timestamps (which under-counted: Dead Space 86 against 97 shown). The timestamp count stays as "reported by timestamp".
- **Run logs** also hold the run's WARN and ERROR lines, the shim's lines and the once-a-minute client frame-gap line (they were only in the main log).
- **Advanced:** the "Game frame pacing fix" switch is labelled "Maximum OpenXR compatibility mode (lower performance)" (same setting, same key).
- **Lab:** the duplicate-timestamp check counts from the first tracked frame; `run.py all` records a scenario that left nothing as FAIL; the frame-generation `pace_*fg23*` scenarios have a frame budget their game rate can reach.

## What ran, and what did not

Lab (3080 Ti builder, mock client, debug/telemetry flavour): host unit tests 26 of 26; the log noise and routing checks (the routing run had no WARN to route); `e2e_modsim_control_ts` (a clean 100 fps stream: 0.03 % of frames repeat a timestamp); `log_level` from the settings file and from the live stdin line; the UI matrix 576 renders and a Dead Space fixture for the new figure; `e2e_installed_layout`, `e2e_log_level_info`, `e2e_log_level_verbose`, `e2e_mirror`, `e2e_baseline` and 20 more scenarios pass; the full UI matrix (576 renders) passes before the Advanced label change. A Linux harness checks the arrow-key logic (11 checks).
**Not run:** this build on a real headset; a game killed with lines still in the shim's ring; the arrow keys on a real pad or controller; the Advanced window with the longer label in the UI matrix; the shim without a running host; the UI log in the real windows; the log export with the new files. **Known failing in the lab, not caused by this build:** `e2e_mirror_desktop` (the builder's screen delivers no picture: the same on 1.3.9), the visionOS client's `sw_*` rate-switch scenarios.

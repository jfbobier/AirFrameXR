## VisionALVR 0.2.0-alpha

**What is new since 0.1.0-alpha: a redesigned frame path.** The streamer used to run one synchronous loop (wait for the game's frame, encode,
send), so a long encode blinded the intake and shifted the phase of the whole chain, which showed as trembling. Now:
- **Staged pipeline**: a clock thread picks the newest complete game frame at each display boundary; an encoder thread and a sender
  thread (sends at the boundary plus the encode time) run apart; the game is released by a **running start** in the runtime
  shim (SteamVR-style), so frames are produced one per display period. A **two-deep frame queue** keeps the older of two bunched frames
  instead of dropping it (GPU-bound games complete frames in bunches).
- Head-pose samples are consumed in order and the predicted display time follows the display grid: far fewer duplicated or skipped
  frame timestamps.
- Real-time GPU scheduling class for the streamer (needs the elevated launcher), headset **discovery** in the streamer (mDNS; the
  Vision Pro's ALVR app does not broadcast), **height calibration** knob and a **hand pose convention** fix (palm/aim were inverted).
- A **pacing lab** in the harness (a Vision Pro display emulation, steady/bursty/spiky app profiles, the benchmark scene as a real
  OpenXR app) and an architecture document (`docs/ARCHITECTURE.md`).

**Final 0.2.0-alpha build: the trembling cause is fixed.** A headset-less test rig built for this release (frame path, display queue and
a pose-correction check on a synthetic head) found that the runtime shim composed the *previous* game frame's picture under the *current*
frame's head pose (a swapchain-index off-by-two inherited from the OVRNull sample code). Any gap or bunching in the head-tracking samples
then became a visible position error while the head moved (still head: no problem, moving head: trembling). The shim now composes the
frame that was just rendered; the rig measures the residual error at about 0.01 degree, and on the headset the trembling is gone.
This zip is the release build (basic logs only; the per-frame debug traces are compiled out).

Alpha of **VisionALVR**: stream PC OpenXR games to **Apple Vision Pro** with the stock **ALVR** app, without
SteamVR, using an encode path written for NVIDIA NVENC.

> [!WARNING]
> **ALPHA SOFTWARE: TEST AT YOUR OWN RISK.** Tested on a real headset by one person, on one PC (RTX 5090) with one Vision Pro.
> Games may crash, fail to start or show a broken image; the stream may stutter. The register script makes the folder your
> PC's OpenXR runtime and adds a firewall rule (`unregister_openxr_runtime.bat` undoes both). Take the headset off if the
> image freezes or judders. Provided "as is", without warranty (MIT).

### Recommended network
A Wi-Fi 6 (or newer) router for the headset in **dumb access point mode** (the first Vision Pro has Wi-Fi 6 on **5 GHz only**: use a 160 MHz channel; 6 GHz is for newer models and the Quest 3), PC on Ethernet, and a **fixed IP for the headset** (DHCP
reservation by MAC address; turn off *Private Wi-Fi Address* for that network on the headset). Details in the
[README](https://github.com/jfbobier/vision-alvr#recommended-network-setup).

### What this project is, and is not
- **Not a competitor to commercial applications**: it offers more options to the VR community, using the open source ALVR as the infrastructure.
- **Game compatibility is not the goal.** For a game that does not work, use **SteamVR + ALVR** (SteamVR is excellent at compatibility and
  configurability). In testing, the vast majority of **UEVR games**, the **Luke Ross mods** and **native OpenXR / VR games** worked; some games
  still have controller issues, crashes or both. SteamVR/OpenVR-only games are not supported.
- **Coming in 0.3**: an autoconfigure tool that proposes the best settings for your headset, PC and network (work in progress on the
  [`0.3` branch](https://github.com/jfbobier/vision-alvr/tree/0.3)).

### Who it is for
- **Windows** PC with an **NVIDIA GeForce RTX 40 series or newer** GPU (older GPUs are refused).
- **Apple Vision Pro** with the **ALVR** app **20.14.x** from the App Store, on the same LAN (Wi-Fi 6, 5 GHz).
- OpenXR games: native OpenXR, UEVR, Luke Ross mods, ... (not SteamVR/OpenVR games).

**Main focus: Apple Vision Pro.** Other headsets with an ALVR client (Quest, Pico, ...) are expected to work, but are **not actively supported** (not tested here; the defaults are tuned for the Vision Pro).

> [!IMPORTANT]
> **If you see a plain green screen when the headset connects, that is normal.** It is the idle frame the streamer sends while no
> game runs. In the ALVR app on the Vision Pro, **set the chroma-key colour to that green (`#00FF00`)** so the green becomes
> transparent (you see your room), and the picture of the game appears once you start an OpenXR game.

### Install
1. Download `VisionALVR-0.2-alpha.zip` below and unzip it anywhere (it is a portable folder; `config\` and `logs\` are
   created inside it).
2. Close SteamVR and ALVR's own launcher (they use the same ports).
3. Run `register_openxr_runtime.bat` once (asks for administrator rights).
4. Run `configure.exe`: open the ALVR app on the Vision Pro, select it, **Pair**. Set the ALVR app's chroma-key colour to
   the "colour when no game runs" (default `#00FF00`).
5. Run `VisionALVR.exe` and keep it open, then start an OpenXR game.

Full guide: [docs/INSTALL.md](https://github.com/jfbobier/vision-alvr/blob/main/docs/INSTALL.md).

### What is in this alpha (as 0.1, plus the above)
- **Streaming**: OpenXR game -> VirtualDesktop-OpenXR runtime -> OVRShim (layers composed into a shared 10-bit frame ring,
  no extra copies) -> NVENC HEVC 10-bit with ALVR's foveated encoding and a foveal QP map -> ALVR 20.14.1 protocol, unchanged.
- **Layers**: projection, quad (head- and world-locked), cylinder and cube layers.
- **Input and audio**: controllers through ALVR's Quest/Touch emulation, haptics, game audio streamed to the headset.
- **Pacing** on ALVR's display clock, frames stamped with the head pose they were rendered for.
- **Idle frame**: a solid colour (default pure green) while no game runs, for the ALVR app's chroma key.
- **VisionALVR.exe** (runtime window): starts the streamer, reconnects to the paired headset, status every 10 s,
  display gamma (default 1.2) plus brightness / contrast / saturation / sharpening, debug logging switch, OpenXR registration
  and GPU checks.
- **configure.exe**: pairing (LAN discovery), settings (resolution, refresh rate, bitrate, foveation, audio, ...), and
  benchmarks: encoder test, network test (finds a clean bitrate for your Wi-Fi), and a quality benchmark that measures picture
  quality vs encode time for ~30 settings on a real 3D scene (proposals are saved; applying them comes in a later version).
- **Logs** in the folder: `logs\VisionALVR.log` (appended by every component) and, with debug on, one `logs\debug\<time>\`
  folder per session.

### Known issues
- The headset displays about 20 % fewer frames than the streamer sends in some games (under investigation); occasional "old" frames and
  tearing with fast head movement.
- GPU-bound games (power-capped GPU) lose frames; one Unity game crashes at start; one UEVR game shows no image.
- Headset discovery (mDNS) and the hand pose convention are new and little tested.

### Reporting a problem
Open an [issue](https://github.com/jfbobier/vision-alvr/issues) with `logs\VisionALVR.log` and the matching `logs\debug\<time>\`
folder (turn debug on in VisionALVR.exe, reproduce, zip the folder), the game and how it is started, GPU and driver.
The logs contain your headset's name and LAN address; remove them if you prefer.

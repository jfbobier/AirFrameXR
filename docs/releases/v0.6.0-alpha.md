# VisionALVR 0.6-alpha (performance pass, in progress)

Same product as 0.5 (see [v0.5.0.md](v0.5.0.md)); this line carries the 0.6 performance work from [docs/PLAN_0.6.md](../PLAN_0.6.md), one item
at a time, each measured in the headset-less rig before it reaches a headset. What is here so far:

- **The game's frame start is gated by the streamer's release (VDXR patch 5).** The OpenXR runtime's own "running start" woke the game's
  `xrWaitFrame` one display period minus 2 ms after the previous release whatever the streamer did, so in every GPU-bound game the CPU ran a frame
  ahead of the release and the GPU throttle, and the render queue sat at 2-3 frames. Now `xrWaitFrame` waits for the release. Rig: one display period
  less between the game's frame start and its GPU completion (55 -> 42 ms at the 1/2 cap, 47 -> 36 ms free-running), same frame rate and repeats. The
  pose is read at `xrWaitFrame`, so this comes off pose-to-photon latency. What to watch on a headset: the shim pacing line's `app cpu` (off its
  0.5 ms floor), client latency, fps in CPU-heavy games. Registry DWORD `ovrshim_vdxr_running_start` = 1 under `HKLM\SOFTWARE\VirtualDesktop-OpenXR`
  restores the old behaviour for an A/B.
- **Frame generation holds its stamp regime** (`video.frame_gen_hold_age`, default on; false restores the old rule). A tracking sample late by more
  than a period makes every later output one period younger until a skip and a bunch move them back: the total latency cycling 67 <-> 77 ms every
  10-20 s on the Vision Pro, a hitch per switch while turning. The 10 s `frame generation samples` line now counts these `regime switches`. Now that boundary repeats once and the regime stays. The headset-less rig, whose simulated uplink is late by over a period several times a
  second, preferred the old rule (more repeats with the hold); a headset with rare switches is where the hold pays. Watch `held` in the samples line.

Nothing else changed: settings, windows, protocol and profiles are 0.5's.

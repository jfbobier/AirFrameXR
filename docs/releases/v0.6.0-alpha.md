# VisionALVR 0.6-alpha (performance pass, in progress)

Same product as 0.5 (see [v0.5.0.md](v0.5.0.md)); this line carries the 0.6 performance work from [docs/PLAN_0.6.md](../PLAN_0.6.md), one item
at a time, each measured in the headset-less rig before it reaches a headset. What is here so far:

- **The game's frame start is gated by the streamer's release (VDXR patch 5).** The OpenXR runtime's own "running start" woke the game's
  `xrWaitFrame` one display period minus 2 ms after the previous release whatever the streamer did, so in every GPU-bound game the CPU ran a frame
  ahead of the release and the GPU throttle, and the render queue sat at 2-3 frames. Now `xrWaitFrame` waits for the release. Rig: one display period
  less between the game's frame start and its GPU completion (55 -> 42 ms at the 1/2 cap, 47 -> 36 ms free-running), same frame rate and repeats. The
  pose is read at `xrWaitFrame`, so this comes off pose-to-photon latency. What to watch on a headset: the shim pacing line's `app cpu` (off its
  0.5 ms floor), client latency, fps in CPU-heavy games. Registry DWORD `ovrshim_vdxr_running_start` = 1 under `HKLM\SOFTWARE\VirtualDesktop-OpenXR`
  restores the old behaviour for an A/B.
- **Frame generation: the stamp regime is counted** (`regime switches` in the 10 s samples line) **and can be held** (`video.frame_gen_hold_age`, default off). A tracking sample late by more
  than a period makes every later output one period younger until a skip and a bunch move them back: the total latency cycling 67 <-> 77 ms every
  10-20 s on the Vision Pro, a hitch per switch while turning. The 10 s `frame generation samples` line now counts these `regime switches`. With the hold that boundary repeats once and the regime stays, but the first Vision Pro night counted five switches a second, so the hold
  only turned them into repeats: off by default, the counters stay.

- **The resolution scale is gone.** It could ask for more than the encoder takes (HEVC: 8192 pixels across, 4096 per eye side by side; a scale of 1.21
  on the Vision Pro's 3552 made the streamer restart in a loop). The settings now take the per-eye size directly and refuse anything over the
  encoder's limit, with the reason; a size the engine still cannot encode is reported as a setup problem, not retried.
- **Advanced settings is a card in the launcher** (it used to be a link at the bottom): the experimental and tuning switches of
  [docs/EXPERIMENTAL_SWITCHES.md](../EXPERIMENTAL_SWITCHES.md), each with when it takes effect (live / streamer restart / next game start). **Uncapped
  frame generation moved there**, marked experimental, out of the streamer window. The old pairing / benchmark tabs are the "Setup tabs" link.
- **Chroma-key passthrough is optional and off by default**, key colour #00FF00 again. With it off the streamer's idle screen is black and the desktop
  mirror is on by default. ALVR has no way for a client to report that it accepted the key (docs/CHROMA_KEY_PROTOCOL.md), so the setup wizard offers it to
  every headset except the Vision Pro, whose App Store app has a fixed key colour and range.
- **Streamer window:** the headset line has three states (red not found, orange-yellow seen on the network, green connected), and a **Main menu** button
  opens (or brings forward) the launcher.

Version number shown: 0.6. Protocol and profiles are otherwise 0.5's (the profiles' passthrough is off, key #00FF00).
